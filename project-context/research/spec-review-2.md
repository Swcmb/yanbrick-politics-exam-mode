## 2. 专项审查一：S-1 的新技术决策能否成立

规格 §6.7 的核心主张：脚本覆盖层收到选项点击 → 找到原生选项 DOM 节点 `.click()` → React 走 `onChange→setState→写盘→UI` 完整链路；脚本只持有"渲染镜像状态"。

### 2.1 成立的部分（不要误判为问题）
**【推测，但为 DOM/React 既定行为】**
1. **程序化 `.click()` 不受遮挡影响**：`HTMLElement.click()` 同步派发 `MouseEvent`，**不做 hit-testing**，不检查元素是否被覆盖、是否在视口内、是否可见。"原生节点被 Shadow DOM 覆盖层遮住"**完全不妨碍** `.click()` 执行。规格这一假设**正确**。
2. **能走 React 完整链路**：`@grant none` 下脚本与 React 共享同一 `document`；原生节点在 light DOM（`#root` 内），`.click()` 派发的事件冒泡到 React root container，触发 `onClick`/`onChange`；若节点是 `<input type=radio/checkbox>`，`.click()` 还会切换 checked 并派发 `input`/`change`。方向比第一版的"直接写 localStorage"**根本性更正确**。
3. **方向对**：真正实现了"复用原生状态/不伪造提交"，与第一轮建议一致。

### 2.2 未关闭的缺口（必须改）

**缺口 A：节点引用失效 / detached node ——规格无应对**
- **【推测，机制可靠】** React 每次 `setState` 会重渲染，选项节点被卸载并重建。若脚本缓存 `load()` 时抓到的节点引用，旧节点变成 detached node，**其上的 click 事件不再冒泡到 React root**，React 处理器不执行 → **click 静默无效**，且用户看到的覆盖层状态会与原生 state 永久错位。
- 规格 §4 存了 `options[].domIndex`，§6.7 用了"**找到**对应原生节点"的措辞，看起来意图是动态定位；但**全文没有写死"每次写回前重新 `querySelector`、检查 `node.isConnected`、禁止缓存节点引用"这条硬约束**。这是规格缺口，不是实现细节——实现者极可能图省事缓存引用。
- **必须改**：在 §6.7 明确写回算法伪代码（重新查询 + `isConnected` 校验 + click 后回读 React 更新后的 `picked` 作成功判据，失败重试/提示）。

**缺口 B：与 D-2 的联合矛盾 ——这是本轮最根本的问题**
- D-2 的处置是"PaperAdapter 一律 API-driven，**不依赖 DOM 是否虚拟滚动**"来关闭读取端；但 S-1 的写回**恰恰依赖目标原生节点存在于 DOM**。
- **【推测】** 若原生整卷页是逐题/虚拟渲染（只挂载当前 1~2 题的 `pb-pq-*` 卡片），那么：脚本从 API 读到第 20 题并显示 → 用户在覆盖层作答 → 脚本要 click 第 20 题的原生选项 → **该节点根本不在 DOM**，`.click()` 无从执行；答题卡任意跳转（§6.5）会把这个问题放大到任意题。
- 规格用"API-driven"关闭了读，却让写重新依赖被绕过的那个未知。**两个决策策略不兼容，规格未察觉，更未处理。**
- D-2 的"静态分析"只证明**接口返回全量数据**，**没有证明原生 DOM 一次渲染全量题卡**。这正是第一轮 D-2 要求实测的原题，被绕过了。
- **必须改（前置门禁）**：实测原生页 DOM 渲染方式（见 R-1）。若虚拟渲染，S-1 方案必须补"先驱动原生翻页定位到目标题、待节点挂载后再 click"的段落，或重新评估整体写回方案。

**缺口 C：`.pb-submit` 选择器未经实测**
- **【事实-规格】** §2.4 的 DOM 命名约定只列了 `pb-pq-${id}`、`pb-*`、`pb-ave`、题型标签，**没有 `.pb-submit`**。§6.7 凭空引入这个选择器作为交卷目标。若选择器错误、或交卷按钮按需渲染（仅末题/仅点入口后出现），交卷 click 直接失败。
- **必须改**：实测确认真实交卷按钮选择器并替换（R-5）。

**缺口 D：脚本覆盖层与原生确认弹窗的层级冲突**
- **【推测】** 若原生交卷有 portal 确认弹窗（挂在 body 下），而脚本 Shadow Host 的 `z-index` 更高，弹窗会被遮挡，用户无法完成原生二次确认 → 交卷卡死。规格未规定层级关系与原生弹窗的交互。
- **建议改（可并入 R-5）**：明确脚本 host 层级低于原生对话框，或提供原生弹窗可点击通道。

### 2.3 S-1 小结
技术机制成立、方向正确，**但"脚本只持有渲染镜像状态"这一架构要真正跑通，前提是目标原生节点随时可被重新定位且可 click**。规格没有为这个前提提供实测证据，也没有防引用失效的硬约束。**判定：部分关闭，不可据此进入实现。**

## 3. 专项审查二：D-2 的 bundle 静态分析推断链条

规格 §2.5：`xe(code)`→`re(chapterCode)`→`Ne(chapter)` 从 `/api/politics/chapters/{code}/answers` **一次拿到完整 `questions[]`**；随机组卷走 `je(code)`→`a.questions`；因此 PaperAdapter 一律 API-driven。

### 3.1 推断链条的四处不严谨

**(1) 证据不可复核（本机事实）**
如 §0.1，项目无任何 bundle 快照或分析记录。用 `xe/re/Ne/je/a` 这类**压缩混淆变量名**描述调用链，**没有代码片段、参数传递、返回值结构**，第三方无法验证推断是否正确。这不是"静态分析确认"，是"口头断言"。→ 见 R-4。

**(2) 绕过了 D-2 的原题，只关了读取端**
第一轮 D-2 要求实测 `querySelectorAll('[class*="pb-pq-"]').length` vs 页面总数，核心未知是**原生 DOM 是否一次渲染全量题卡**。规格改为 API-driven，读取端确实不再依赖 DOM（这点更稳健，认可）；但如 §2.2 缺口 B，写回端重新依赖它。**D-2 未真正关闭。**

**(3) 接口语义疑点 + 随机组卷分支零证据**
- **【推测】** `/api/politics/chapters/{code}/answers`：命名字面是"答案"，**是否返回含 `stem`/`options` 的完整题目**未坐实。规格 §2.3 把题目字段笼统归于"组件与接口"，未给该接口的响应 JSON 结构。若它只返回 id→答案映射，"一次拿完整题目列表"就不成立。
- **任务明确追问"随机组卷（je 分支）题目来自哪"**：规格答 `je(code)`→`a.questions`，但 `a` 指代什么（模块变量？全局 state？API 响应字段？）、对应哪个 API 路径、响应结构如何，**全部无证据**。mock 与 real 同归 PaperAdapter，题目来源却不同，必须分别坐实。

**(4) 最严重：脚本独立 fetch 与原生页面会话/种子的一致性 ——规格完全未触及**
- **【推测，风险高】** 随机组卷（mock 类）的题目集合很可能由服务端按 `paperAttemptId`/session/随机种子决定。原生页面加载时服务端已确定这套题；脚本再独立 `fetch` 一次 `je(code)` 对应接口，**若该接口有状态（每次调用触发新一次随机抽题），脚本会拿到与原生页面不同的题目集合**。
- 后果：脚本覆盖层显示的题 ≠ 原生交卷判分的题，用户按脚本显示的题作答，原生却按另一套题判分 → **直接违反"数据真实""不伪造提交结果"两条硬约束**，且用户完全无感知。这是比 D-2 原问题更严重的隐患。
- **必须核实**：`chapters/{code}/answers` 与 `je(code)` 是**幂等**（按 chapter 固定返回全量题库，脚本可安全独立 fetch），还是**有状态**（按 attempt 随机）。若后者，禁止脚本独立 fetch 题目，必须从原生状态/原生 DOM 读取当前题目集合，并重做 §2.5 的结论。
- **附带**：`paperId` 取 URL code（§4），而接口入参是 `chapterCode`，两者的映射/转换规则规格未明确。

### 3.2 D-2 小结
处置思路（API-driven）本身**优于**原方案的"实测 DOM"，这点应肯定；但**证据链不可复核、只关读取端、随机组卷分支无证据、会话一致性未考虑**四个问题使它不足以支撑"PaperAdapter 可以进入实现"的结论。**判定：未真正关闭。**
