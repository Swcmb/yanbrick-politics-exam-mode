## 0. 审查方法与证据分级

本报告严格区分三类陈述，全文用标签标注：

- **【事实-规格】**：直接引自规格文本或用户提供的"已实测事实"，可核对，不负责其真伪。
- **【事实-外部】**：来自可查证的外部资料（Tampermonkey 注入/沙箱机制，已联网核实），或本机文件系统事实。
- **【推测】**：本人的工程判断，**尚未在目标站点实测**，实现前必须按每条建议验证。

已核实的环境事实：
- **【事实-外部】** 项目目录内仅有 `LICENSE` 与本规格，不存在规格反复引用的"任务文件"及其"第十一节验收清单"。规格 §8.3 把验收标准外包给一个**当前不可见的文件**，这是个可追溯性缺陷。
- **【事实-外部】** Tampermonkey 在 USERSCRIPT_WORLD 注入可绕过 CSP；`@grant none` 时脚本直接运行在页面上下文、可访问完整 `document`/`window`；`@grant GM_*` 时脚本在沙箱中但 DOM 访问仍是完整的；SPA 场景必须自行 `waitForElement` + `MutationObserver`；`GM.xmlHttpRequest` 跨域需 `@grant` + `@connect`，同源不需要；MutationObserver 必须 `disconnect`/防抖否则泄漏。（来源：Tampermonkey 文档与社区资料，联网核实于 2026-11-17）

## 1. 可行性

> 维度判定：**需修改**（无阻断，但有两处被规格完全忽略、可能导致脚本根本不运行的风险）

### F-1 【事实-外部 vs 规格】CSP：规格零覆盖，但这是"脚本能否运行"的前置条件
- **规格现状**：全文未提 Content-Security-Policy。
- **理由**：Tampermonkey 通常在 USERSCRIPT_WORLD 注入从而绕过 CSP（已核实），但若目标站响应头是极严格策略（如 `script-src 'self'` 且无 `unsafe-eval`、未放行脚本管理器钩子），存在注入失败、脚本静默不执行的真实案例（已核实）。本规格直接假设"脚本装上去就能跑"。
- **建议改法**：实现第一步先用浏览器 DevTools Network 读取 `https://yanbrick.com/politics` 的响应头，记录 `content-security-policy`（含 `script-src`/`worker-src`/`connect-src`）。若存在限制，明确采用 `@grant none` 或 Tampermonkey "UserScripts API" 注入模式，并在规格里写注入模式选型与实测结论。**此项列为实现前置门禁。**

### F-2 【事实-外部】同源 fetch 即可，不需要 GM.xmlHttpRequest 权限
- **规格现状**：任务背景把"GM.xmlHttpRequest 权限"列为可能被忽略的限制，规格 §3/§5 未明确取数通道。
- **理由**：`/api/politics/*`、`/api/state`、`/api/answer` 全是同源路径。**【推测】** 油猴脚本在页面 origin 下用普通 `fetch` 即自动携带登录 cookie（浏览器默认 `credentials: same-origin`），无需 `@grant GM_xmlhttpRequest`、无需 `@connect`、无需用户额外授权。滥用 GM 权限反而增加安装摩擦和跨域配置面。
- **建议改法**：明确"取数一律用同源 `fetch`，仅在确需跨子域时才申请 `GM.xmlHttpRequest` + `@connect`"，删除对 GM 权限的泛化依赖描述。

### F-3 【事实-外部】Shadow DOM 键盘事件 + 捕获阶段拦截的具体风险
- **规格现状**：§6.3 "与网站快捷键冲突时脚本优先（捕获阶段），但放行无关键盘组合"。
- **理由**：脚本自建的 Shadow DOM 内部键盘事件 `composed: true`，监听在 `document` 捕获阶段可以拿到，技术上成立（已核实）。但"脚本优先"若在捕获阶段 `preventDefault`/`stopPropagation`，会**连带破坏原生按钮的键盘激活**（Tab 聚焦 + Enter 触发），与 §6.3 自身"所有键盘操作有鼠标等价入口"及无障碍目标冲突；且"有关键/无关键"的判断标准未定义，无法测试。
- **建议改法**：把"脚本优先"改为**显式白名单**：仅拦截 A/B/C/D、1/2/3/4、Enter、←/→、Esc（且仅在非输入焦点态）；其余按键（尤其 Tab、Ctrl/Cmd+R、F12、Ctrl/Cmd+L 等）一律放行；给出"按键 → 是否 preventDefault"的真值表作为可测规格。

### F-4 【推测】题干 innerHTML 注入后，公式/图片样式在 Shadow DOM 中可能丢失
- **规格现状**：§3/§4 "题干 innerHTML 原样注入（图片/表格/公式保留）"。
- **理由**：若站点用 KaTeX/MathJax 渲染公式，其样式表挂在 light DOM / document 级；Shadow DOM 样式隔离后，`innerHTML` 里残留的公式节点很可能失去样式或根本不渲染。规格把"公式保留"当成 innerHTML 的天然结果，这是未经证实的假设。图片若为相对路径，在 Shadow DOM 中仍按 document URL 解析，一般 OK；但站点若用懒加载/CSS 背景，需要验证。
- **建议改法**：取一道含公式的真实题实测。若公式丢失，方案二选一：(a) 把站点公式 CSS 通过 adoptedStyleSheets / `<link>` 引入 Shadow Root；(b) 放弃重注入题干，改为把原生题干节点 `cloneNode(true)` 移入 Shadow DOM 并保留其已渲染状态。规格需写明选定方案。

### F-5 【推测】SPA 路由切换需要"重新 detect + 清理旧 Shadow Host"
- **规格现状**：§3 提到 MutationObserver，但未提 history 拦截、旧实例清理。
- **理由**：SPA 路由切换会改 DOM，MutationObserver 可捕获，但存在两类坑：(a) 脚本自身插入的 Shadow DOM 会触发 observer，造成无限循环/抖动（已核实为常见坑）；(b) 路由切换后旧题的 Shadow Host 若不卸载，会残留、重复渲染。规格未规定生命周期。
- **建议改法**：observer 必须防抖 + 过滤 `addedNodes` 中来自自身 Shadow Host 的节点；每次路由变化执行 `detect() → 若类型/ paperId 变化则销毁旧实例并重建`；`beforeunload` 时 disconnect。写入规格 §3。

## 2. 数据真实性（最关键维度）

> 维度判定：**需修改，且含 1 项阻断级未知**。结论先行：**规格没有在假设一个"做不到"的数据源，但它混淆了"审查工具的能力边界"和"油猴脚本的能力边界"，导致取数机制含糊其辞，并把一个关键未知（整卷是否一次性渲染）留到了实现期。**

### D-1 【事实-外部 vs 事实-规格】核心澄清：油猴脚本 ≠ 浏览器自动化工具
- **用户给的限制**："浏览器工具无法在页面执行任意 JS 读取完整 DOM（只能读过滤后的可见 DOM），无法直接读 cookie。"
- **【推测，但机制已核实】** 这个限制属于**浏览器自动化/审查工具**，不是目标网页的限制，更不是油猴脚本的限制。油猴脚本：
  - 运行在页面上下文（`@grant none`）或 USERSCRIPT_WORLD（`@grant GM_*`），**能执行任意 JS**（已核实 Tampermonkey 绕过 CSP 注入）；
  - 能用 `document.querySelectorAll` 访问**完整 DOM**，不受任何"过滤视图"影响（已核实）；
  - 同源 `fetch('/api/politics/...')` **自动携带登录 cookie**，因为脚本就在页面 origin（已核实 `credentials: same-origin` 为默认值）；
  - 能读写同源 `localStorage`。
- **判定**：因此"从网站真实数据读取"**技术上可达成**。规格的潜在错误在于：若作者在写 Adapter 时下意识沿用了"只能看过滤 DOM"的心智模型（例如只抓可见文本、认为拿不到 React props/隐藏节点/接口原始 JSON），Adapter 会建立在不必要的自我设限上。**规格必须显式打破这个混淆。**
- **建议改法**：在 §2 或 §5 增加一节"取数通道"，明确三种数据源的优先级与用途：
  1. **同源 API fetch（首选，拿结构化真值）**：题目列表、题目详情、答案、分值字段、均分原始值；
  2. **完整 DOM 抓取（补充，拿"以页面实际渲染为准"的显示值）**：`pb-ave` 均分文本、`已作答 n / N`、`+1分` 标签、题干/选项 HTML；
  3. **原生 localStorage 草稿（拿 startedAt / picked）**。
  并写明"Adapter 运行在页面上下文，可访问完整 DOM 与同源接口；审查工具的限制不适用于脚本"。

### D-2 【推测｜阻断级未知】整卷 33 题是否一次性渲染？决定 PaperAdapter 存亡
- **规格现状**：§2.3/§5 假设 PaperAdapter 能"读取整卷题目列表"，§4 `total = questions.length`。
- **理由**：若整卷采用虚拟滚动 / 逐题懒加载（只渲染当前 1~2 题），则：
  - DOM 抓取拿不到完整题目列表，`questions.length` 可能为 1，`total`、`答题卡网格`、`已作答 n / N` 全部崩塌；
  - 要拿到全部题，必须改为"从 API 拿题目 ID 列表 + 逐题驱动原生翻页抓取"或"纯 API 取数"，这与规格"读 DOM 列表"的方案不同。
  - 规格 §2.2 写"33 题 / 50 分场景"、DOM 命名 `pb-pq-${id}` 暗示一次渲染全部题卡，但**没有实测证据**。
- **建议改法（实现前门禁）**：打开任一真实整卷页，在 DevTools Console 执行 `document.querySelectorAll('[class*="pb-pq-"]').length`，与显示的"共 N 题"比对。若相等 → 规格方案成立，把该实测数字与命令写进规格 §2；若不等 → **PaperAdapter 必须改为 API-driven**，且"答题卡显示题干"的需求要降级为"仅显示题号 + 三态"。**此项未验证前，PaperAdapter 不应进入实现。**

### D-3 【推测】分值 `score` 的真实来源未在规格中闭合
- **规格现状**：§2.3 "单题分值可能来自题目自身 `score` 或由整卷满分/题型推导，**以页面实际渲染为准**"；§6.2 "分值取不到显示'—'"。
- **理由**：这实际上是承认"不知道分值从哪来"。"以页面渲染为准"若指 `+1分` 标签，则必须明确抓哪个选择器、多题如何映射。规格没有给出分值 DOM 选择器或接口字段验证结论。`fullScore` 同理。
- **建议改法**：实测记录：(a) 单题分值在 DOM 的选择器/类名（规格只给了题型标签的模板，没给分值标签的选择器）；(b) `/api/politics/questions/{id}` 或题目列表接口是否返回 `score`/`fullScore`。若接口不返回，明确"分值一律取 DOM 的 `+N分` 标签，按题卡容器归属映射"。禁止"由满分/题数反推单题分值"——那会伪造数据。

### D-4 【事实-规格】均分 `pb-ave` 可达性 OK，但"不本地计算"需落实到测试
- **理由**：均分由服务端渲染在 `.pb-ave`，完整 DOM 可达（结合 D-1），API 也可能返回原始值，取数本身无障碍。风险在于实现者为了"信息栏好看"而本地算 `已得分/题数` 冒充均分——规格 §6.2 已明令禁止，这条是好的。
- **建议改法**：把"均分必须与 `.pb-ave` 文本逐字符一致（含 `N / 50` 的分母）"写成一条可自动化的断言（见 §5 测试分层）。

## 3. 复用原生状态

> 维度判定：**需修改，含 1 项高优先级风险**。核心问题：规格默认"写 localStorage = 复用原生状态"，但这在 React SPA 里通常不成立。

### S-1 【推测】直接写 localStorage 不会更新 React 内存 state → 交卷可能提交旧数据
- **规格现状**：§6.4 "答案复用原生 `pol:paper-draft:*` 键"；§6.7 "写全部答案 → 调用网站原生交卷流程"。
- **理由**：React 组件在挂载时把草稿读进 state，**之后 state 是真相源**。脚本直接改 localStorage：
  - 不会触发 React 重渲染（界面与脚本覆盖层不一致，但覆盖层遮住了，用户看不到，问题被掩盖）；
  - **关键**：若原生交卷函数读的是 React state（SPA 常见写法），脚本写入的 localStorage 会被忽略，提交的是旧/空答案 → 直接违反"不伪造提交结果""数据真实"。
  - 规格 §2.4 "交卷时把 picked 归一化提交"暗示交卷读 localStorage，但这是**推测、未验证**。更糟的是反向竞态：React 在任意 state 变更时把 state 序列化回 localStorage，可能把脚本刚写入的答案冲掉。
- **建议改法（必须改，优先级最高）**：
  1. **实测**原生交卷的数据源：用原生界面手动答一题但不点交卷，改 localStorage 中的 `picked`，点原生交卷，看提交的答案来自哪。或直接静态读 `Paper-*.js` 的 submit 函数。
  2. 写回策略改为**以"驱动原生按钮"为主**：脚本覆盖层收到选项点击 → 找到并 `.click()` 对应的**原生选项 DOM 节点**（原生节点仍存在于 light DOM，只是被覆盖），让 React 走 `onChange → setState → 写 localStorage → 更新 UI` 的完整链路。这才是真正的"复用原生状态"。
  3. localStorage 直接写入仅作为**恢复/补偿**（如刷新后注入 picked），且写入后要触发一个原生可读的事件或再点一次原生按钮以同步 state。

### S-2 【事实-规格 vs 推测】原生草稿键没有"当前位置/提交状态"字段
- **规格现状**：§6.4 把"答案、**当前位置、开始时间、提交状态**"全部塞进原生 `pol:paper-draft:*`。
- **理由**：【事实-规格】该键的值形状是 `{ startedAt, picked, ... }`，原生并不定义"当前位置""提交状态"字段。往里塞自定义字段属于无根据扩展：可能被原生组件忽略、被覆盖，或在 24h 过期逻辑里被误判。
- **建议改法**：职责分离——原生键只同步 `startedAt` 与 `picked`；把"当前位置(currentIndex)"、"提交状态(submitted)"、"草稿纸"放到脚本自己的独立键 `pol:immersive-state:${paperId}`。规格 §4 `ExamModel` 本已区分这些概念，§6.4 的持久化映射需同步修正。

### S-3 【推测】"调用原生交卷流程"未定义调用方式，且存在双重确认
- **理由**：规格只说"调用原生交卷"，没说是 `.click()` 原生按钮还是 fetch 提交接口。若脚本自带确认面板（§6.7），而原生交卷也有确认弹窗，会出现"双重确认"；若直接 fetch 提交接口，则绕过原生 state 校验，可能缺字段（如 `paperAttemptId`、`secs`）。
- **建议改法**：明确为"程序化点击原生交卷按钮"，去掉脚本自带确认面板或改为"只统计不确认，确认交给原生弹窗"；提交后以原生的成功回调/DOM 变化作为成功判据，**不自行显示"提交成功"**（呼应"不伪造提交结果"）。

## 4. 可测试性

> 维度判定：**需修改**。规格的"真实浏览器测试"缺一个关键前提和一个关键中间层，按其原文无法在给定约束下落地。

### T-1 【推测】"Playwright 复用 deeplearning 环境"没有登录态就会空跑
- **规格现状**：§8.2 "四种答题界面各加载一次"，隐含测试环境能访问登录后的真实页面。
- **理由**：用户明确约束"没有 Playwright 登录态、无法在目标页执行 JS"。若无 `yanbrick.com` 的登录 cookie/storageState，Playwright 打开 `/politics/paper/real-YYYY` 只会跳登录页，§8.2 的 8 类测试全部无法执行。规格没有写这个前提，也没有无登录态时的降级路径。
- **建议改法**：明确真实站点测试的**前置条件**：用户提供 `storageState` JSON（Playwright `browser.newContext({ storageState })`）或导出 cookie。若用户不提供，§8.2 全部标记 `NOT RUN` 并写明原因（§8.3 已有该机制，需真正应用）。

### T-2 【推测】缺失"本地 fixture + API mock"集成层，这是无登录态下唯一能测全流程的方式
- **理由**：单元测试（§8.1）只测纯函数，测不到"detect → 渲染 → 答题 → 交卷"的端到端链路；真实测试（§8.2）又卡登录。**中间层缺失**。
- **建议改法**：新增 §8.2.0"集成测试（无需登录）"：
  - 用一份本地 HTML fixture 复制四种界面的**真实 DOM 结构**（class 名、`pb-pq-${id}`、`.pb-ave`、`+1分` 标签等）；
  - Playwright `page.route('**/api/politics/**', route => route.fulfill({ json: 录制的真实响应 }))` 注入真实 JSON；
  - 在此环境跑脚本，验证 detect/load/一屏一题/键盘/交卷/防重复。
  - 这样即使没有登录态，也能覆盖规格 80% 的行为断言，且 fixture 可用"从真实页面复制的 DOM 快照"生成（注意与 D-1 的"审查工具过滤 DOM"配合——只抓结构，不依赖抓全量数据）。

### T-3 【推测】单元测试与真实测试的分工需明确
- **建议改法**：在 §8 增加分工表：
  - **Node 单测**：解析器、状态机、键盘过滤、草稿纸笔画栈（纯逻辑，无 DOM/无网络，确定性高）；
  - **Playwright + fixture**：DOM 适配、事件流、SPA 生命周期、持久化读写（可控、可重复）；
  - **真实站点（有登录态）**：仅测"接口返回真实数据、原生交卷真的成功、均分与页面一致"这类**必须真实环境**的断言；
  - 每层标注"测什么 / 不测什么 / 前置条件"。

### T-4 【事实-规格】§8.3 引用不可见的"任务文件第十一节"
- 见 §0：当前项目无该文件。建议把验收清单**内联到规格或本报告可访问的附件**，否则"逐项 PASS/FAIL/NOT RUN"无基准。

## 5. 兼容性

> 维度判定：**需修改**。4 适配器 + Fallback 的方向对，但有几处明确边界遗漏和一个内部矛盾。

### C-1 【推测｜高】"total = questions.length"与"逐题流"矛盾
- **规格现状**：§4 `total = questions.length`；§2.2 把 `practice` 描述为"逐题流"。
- **理由**：逐题流页面任一时刻可能只有 1 道题在 DOM，`questions.length` 会等于 1，导致顶栏 `已作答 X / N`、答题卡网格全错。真实的总数应在"已作答 n / N"或接口里。
- **建议改法**：`total` 的来源按 kind 分别定义：paper/mock 取接口 `questions.length` 或页面 "共 N 题"；practice/book 取页面 "已作答 n / **N**" 的分母或接口字段。**禁止统一用 `questions.length`。** 与 D-2 联动。

### C-2 【推测】选项硬编码 A–D / 键盘 1–4
- **规格现状**：§4 `key: "A"|"B"|"C"|"D"`；§6.1 键位 1/2/3/4。
- **理由**：与题干"不硬编码"精神冲突。考研政治选择题通常 A–D，但规格未提供"若出现 E 选项"的策略，类型系统直接封死。
- **建议改法**：`key` 放宽为 `string`，选项数量取真实 `options.length`；键盘映射按 `options.length` 动态生成（1..n），并在 UI 显示对应键位提示。

### C-3 【推测】未覆盖的页面/状态
- **理由**：规格列了 4 类路由，但以下边界未说明，均为"所有答题界面"的合理子集：
  - **交卷后的解析页 / 错题回顾页**：用户停在这些页面时，Fallback 应识别并降级提示，不能破坏原页面；
  - **列表页**（`/politics/books`、`/politics/bank/*` 根）：无题目，需正确判定"无可识别题目"并提示；
  - **登录失效 / API 401**：`load()` 失败的处理与提示；
  - **草稿 24h 过期**：`startedAt` 过期后原生草稿失效，脚本是重新计时还是提示重开（规格完全未提）；
  - **同一 paperId 多标签页并发**：localStorage 竞态（与 S-1 同类）。
- **建议改法**：在 §5/§9 增补一张"边界与降级表"，逐项给出识别方式与行为；至少覆盖解析页、列表页、401、过期 4 项。

### C-4 【推测】PracticeAdapter 的"即时判分"语义与"复用不改判分"需更清晰
- **规格现状**：§5 PracticeAdapter "复用同一写路径，不自行改变判分语义"。
- **理由**：方向正确，但"即时判分"意味着练习模式一旦作答就**不可撤回**（POST `/questions/{id}/answer/log`）。若脚本的键盘误触（快速连按）触发了原生写入，会造成不可撤销的判分记录。这与 §6.1 的"防连按"直接相关但规格未联动。
- **建议改法**：明确"练习模式下，选项点击需经防抖确认（如 150ms）再驱动原生写入"，并把即时判分风险写进 §9 边界。

## 8. 总体裁决

### **APPROVED_WITH_CHANGES**

规格的**架构方向正确**（适配器归一化 + Shadow DOM 呈现 + 复用原生提交），不存在不可实现的根本障碍；但**当前版本不可直接实现**，须完成以下修改后再进入编码。

### 8.1 必须改（BLOCKING，逐条关闭后才允许实现）

1. **【D-2】实测整卷题目是否一次性渲染**（`document.querySelectorAll('[class*="pb-pq-"]').length` vs 页面显示总数）。若虚拟滚动，PaperAdapter 改 API-driven，答题卡降级为"仅题号+三态"。
2. **【D-1】在规格中明确取数通道**：同源 fetch 为主、完整 DOM 为辅、原生 localStorage 补计时；显式声明"脚本可访问完整 DOM 与同源接口，审查工具限制不适用"。
3. **【S-1】实测原生交卷读 state 还是 localStorage**，并把写回策略改为"驱动原生选项/交卷按钮 click"，localStorage 仅作恢复补偿。
4. **【T-1/T-2】补齐测试分层**：新增"fixture + API mock"集成层；明确真实站点测试需登录态，否则标 NOT RUN。
5. **【C-1】修正 `total` 来源**：paper 用题目列表长度/页面总数，practice/book 用"已作答 n / N"分母或接口字段，禁止统一用 `questions.length`。

### 8.2 建议改（强烈建议，不阻塞但降低返工）

6. **【F-1】实测并记录目标站 CSP 响应头**，据此确定注入模式（运行前置门禁）。
7. **【F-3】把键盘"脚本优先"改为显式白名单 + 真值表**，避免破坏原生键盘可达性。
8. **【S-2/S-3】状态键职责分离**（原生键只放 startedAt/picked），交卷确认交由原生，不自行显示成功。
9. **【C-2/C-3/C-4、F-4、F-5、Q-1..Q-8】** 修正类型定义、补边界降级表、公式样式方案、SPA 生命周期、动效降级优先级、验收清单内联。

### 8.3 说明
- 以上所有"实测"动作均为**只读浏览器操作**（打开页面、看 DOM 数量、看响应头、手动答一题），不修改用户项目文件、不提交任何答案、不改服务器状态；可在用户确认登录态可用后安全执行。
- 本报告未修改设计规格本身，仅新增本审查报告。
